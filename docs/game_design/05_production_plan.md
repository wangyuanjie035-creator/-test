# 开发路线

## 推荐路线

先做文档和纸面原型，再做 Godot 最小可玩版本。原因是卡牌构筑游戏的核心风险通常不是渲染，而是循环、数值和内容分类是否成立。

## 阶段 P0：设计框架

目标：让所有人对游戏是什么、先做什么、不做什么达成一致。

交付物：

- 项目章程。
- 核心循环文档。
- 卡牌和构筑框架。
- 局外成长文档。
- 内容池。
- 决策记录。

验收：

- 能用一段话说明游戏。
- 能画出单局循环。
- 能列出 MVP 需要的最少卡牌、事件和 Boss。

## 阶段 P1：纸面原型

目标：不用完整程序，先验证核心规则是否好玩。

交付物：

- 30 张基础卡。
- 3 个 Boss。
- 5 个事件。
- 简化数值表。
- 一份试玩记录。

验收：

- 一局可以在 15 分钟内跑完。
- 玩家每 2 到 3 回合有一个有意义选择。
- 坏结局结算能让玩家想再开一局。

## 阶段 P2：Godot 原型

目标：实现最小可玩闭环。

建议模块：

- 卡牌数据资源。
- 战斗管理器。
- 抽牌、弃牌、消耗区。
- 玩家资源面板。
- 敌人意图与阶段目标。
- 奖励选择界面。
- 履历结算界面。
- 简单存档。

验收：

- 可以从主菜单开始一局。
- 可以完成至少三个节点和一个 Boss。
- 可以失败并进入履历结算。
- 可以解锁至少一个局外内容。

## 阶段 P3：垂直切片

目标：让游戏开始具有完整气质，而不只是功能演示。

交付物：

- 像素风 UI 第一版。
- 至少 80 张卡。
- 至少 15 个事件。
- 至少 6 个 Boss。
- 3 个构筑流派能稳定成型。
- 音效和基础音乐。

验收：

- 单局 30 到 45 分钟。
- 玩家能明确感知不同导师和方向的差异。
- 至少一种坏结局会转化为下一局明显不同的开局选择。

## 阶段 P4：内容扩展和平衡

目标：扩大学科方向、导师风格、事件线和结局。

重点：

- 增加跨学科路线。
- 增加延毕线内容。
- 增加前辈传承系统。
- 建立自动化数值检查或调试面板。
- 开始外部试玩。

## 阶段 P5：打磨与发布准备

目标：稳定体验，减少理解成本和重复疲劳。

重点：

- 教程和首局引导。
- UI 动效和手感。
- 文案统一。
- 存档兼容。
- 性能和输入体验。
- 打包发布流程。

## 每个功能的文档要求

每个功能开始前，复制 [templates/feature_spec_template.md](templates/feature_spec_template.md) 并填写：

- 目标体验。
- 系统规则。
- 数据结构。
- UI 和资产需求。
- 验收标准。
- 风险和开放问题。
- 实现后验证记录。

## 近期最小任务清单

1. 确定正式工作名。
2. 确定 MVP 阶段只做硕士线，还是直接包含博士线。
3. 设计 30 张基础卡的第一版数值。见 [specs/001_mvp_card_set.md](specs/001_mvp_card_set.md)。
4. 设计开题、中期、盲审三个 Boss 的机制。见 [specs/002_mvp_boss_set.md](specs/002_mvp_boss_set.md)。
5. 建立 Godot 的数据目录和卡牌资源格式。见 [specs/004_godot_data_model.md](specs/004_godot_data_model.md)。
6. 实现最小战斗界面。
7. 实现一次失败结算和一次局外解锁。
